# External review, October 2026: what was true, and what to do about it

An external automated review of the whole repository arrived on 02-Oct-2026, covering
the frontend, the canvas engine, the CRDT and document model, the MCP integration, the
API, persistence, realtime, security, testing, deployment and documentation. It raised
nineteen findings over eight severity-ranked sections.

This file records which of them survived checking against the source, which did not, and
what is worth doing. It exists because the review's own best finding is that a reader
cannot tell current architecture from historical intent here, and answering a review
from memory a month from now would repeat exactly that mistake.

It is a point-in-time document, not a second design doc. `docs/core/ARCHITECTURE.md`
remains the only long-lived one. When every item below is either done or explicitly
dropped, this file goes away.

## How the findings were checked

Every claim was read against the manifests, the source and the test suite rather than
taken on its face, and each verdict below cites what settled it. That matters more than
usual here: the review was written from the repository's surface and plainly did not
read `docs/DECISIONS.md` or the milestone sections at the end of ARCHITECTURE, where
roughly half of what it raises is already recorded, measured, or decided against.

That is not only the review's failure. It is the drift problem it identifies in its own
section 18, arriving as evidence for itself. A reader who stops at ARCHITECTURE section 1
gets a stale picture, and that is precisely what happened. The table that misled them
was corrected in `06833ec`; the mechanism that let it rot for six milestones is item 2
below, and is the reason that item is not optional.

## The findings, one at a time

### Done in 1.26.0: MCP was coupled to the web application's internals (finding 4)

The review asks for a shared document package both the app and the MCP server depend
on, instead of the MCP server reaching into the app. This is confirmed, and the real
shape is worse than the review describes. The imports are deep relative traversal out
of the package:

```
packages/mcp/src/look.ts:19    from '../../../apps/web/src/doc/interchange'
packages/mcp/src/plan.ts:27    from '../../../apps/web/src/doc/mutations'
packages/mcp/src/room.ts:20    from '../../../apps/web/src/doc/mutations'
packages/mcp/src/server.ts:39  from '../../../apps/web/src/doc/mutations'
packages/mcp/src/tidy.ts:28    from '../../../apps/web/src/doc/mutations'
```

Five files, four modules, and a package depending upward on an app.
`packages/mcp/package.json` declares no dependency on the web app at all, so this is an
undeclared dependency that works only because esbuild bundles the result.
`packages/mcp/src/snapshot.ts:109` also mirrors `apps/web/src/canvas/style.ts` by hand,
which is the duplicated document behaviour the review credits the project with having
avoided.

The sharing itself is right and worth keeping: one mutation implementation means an AI
edit and a human edit take the same path, which is the same principle as the canvas
never reading through React. Only the direction of the dependency is wrong.

#### How it was fixed

Done in 1.26.0. The shape of the fix was settled by scoping it before moving anything,
because the worry on record was that this "moves the only write path".

**The cluster turned out to be closed**, which is what made it a contained change rather
than the risky one it looked like. `mutations`, `interchange` and `richText` import each
other, `yjs` and `@meadow/schema`, and nothing else, with exactly one exception:
`mutations.ts` imported `BoardRole` from the web app's REST client, and it was a
type-only import of a four-name union that the MCP server had separately written out for
itself. Nothing in the three modules touches a browser global, so the package is
environment-neutral and the MCP server can run it under Node unchanged.

**The boundary drawn** was "reads or writes a Y.Doc and needs neither a browser nor
React". That moved four files into `packages/document-core/src`:

| Moved | Why |
|---|---|
| `mutations.ts` | the write path itself |
| `interchange.ts` | a live document to and from the file format; mutually recursive with mutations |
| `richText.ts` | `Y.XmlFragment` to nodes and static HTML; pure yjs |
| `roles.ts` (new) | `BoardRole`, which `createDocSession` and `roleCanWrite` gate on |

and deliberately left four behind in `apps/web/src/doc`: `useObjects.ts` (a React hook),
`engineHost.ts` (imports the canvas engine), `clipboard.ts` (web interaction, and it
depends on the package rather than the other way round), and `schema.ts`, which is an
app-facing re-export shim carrying one UI constant. The tests moved with their subjects:
`mutations`, `interchange`, `richText` and `convergence` to the package, while
`arrows.test.ts` stayed because it imports canvas helpers.

**`BoardRole` now has one definition**, in the package that gates on it, re-exported by
both API clients so no call site moved. Removing the duplicate was not incidental: a
union copied into two files is the first thing a single write path is supposed to
prevent.

**What this exposed.** The undeclared dependency was load-bearing in a way the review
did not reach. The MCP server's *tests* imported the web app by the same deep relative
paths, and nothing typechecked them against a manifest, so the first full test run after
the move failed on six files that `pnpm -r lint` had passed clean moments earlier. That
is the concrete cost of the arrangement: the coupling was invisible to every tool that
reads a manifest, and only a runtime import resolved it.

**Verified**: `pnpm -r lint` clean, 457 tests passing (126 in the new package, 278 in
web, 53 in MCP), `pnpm --filter web build` clean, and all three production images
building from a clean context: web (`--target runtime` and the dev stage), MCP, and API.
The MCP image was run and answered `/healthz` reporting 1.26.0. The end-to-end scripts
were not run; they need a live stack.

**What the first round of verification missed, and the lesson in it.** Typechecks, unit
tests and a local `vite build` all passed while the change was still unshippable, because
none of them read a Dockerfile or the CI workflow. Both image builds copy workspace
manifests one at a time to cache the install layer, so a new package that nothing copies
fails `--frozen-lockfile`; and CI named each package in a `--filter` flag, so the 126
tests that moved into the new package would have stopped running while the job still
reported green. A refactor that moves files across package boundaries is exactly the kind
that breaks build wiring rather than code, and the wiring has to be checked in the same
pass. CI now uses `pnpm -r` so a list cannot go stale again.

One detail worth keeping, because it is the kind of thing that compiles in one package
and not the other. `BoardRole` could not be published with a bare
`export type { BoardRole } from '@meadow/document-core'`: that re-exports the name
without binding it in the file, and both API clients use it in their own signatures, so
each needs the `import type` as well. `tsc` catches it, which is the reason the web
build is in this list and not just the test suites.

**What the fix did not take on.** `packages/mcp/src/snapshot.ts:109` still mirrors the
canvas style tokens by hand. Moving them into `document-core` would put render
configuration in the document layer, and moving them into a package the canvas imports
would cut against the canvas staying independent and extractable. It stays a deliberate
duplication with a comment naming its source, and is worth revisiting only if a third
copy appears.

### Valid: nothing carries an operation id, and AI mutations are not audited (findings 10, 11)

Confirmed absent. No `operation_id`, `request_id` or correlation id exists anywhere in
`services/api/app`. Dropped writes are logged with the board and a running count
(`app/realtime/guard.py:262`), so a tampered client is visible, but there is no way to
answer "which MCP call changed this object" after the fact.

This is the most useful suggestion in the review after finding 4. It is additive, it
does not touch the locked CRDT schema, and once agents can edit shared documents the
question gets asked eventually.

### Done in 1.27.3: Redis failure behaviour was implemented but not written down (finding 16)

The behaviour is deliberate and already decided, site by site.
`app/services/session_events.py:66` swallows any Redis failure as non-fatal; line 97
answers False on failure so the request is let through;
`app/realtime/search_queue.py:53` and `:91` catch `RedisError` and `OSError` and fail
open. What did not exist is one statement of what degrades when Redis disappears. Every
infrastructure dependency should have a stated failure mode, and this one had several
unstated ones.

#### How it was fixed

Done in 1.27.3, in `docs/DECISIONS.md`. The item was scoped at "around twenty lines"
collecting "the three existing fail-open decisions", and both halves of that were wrong.
There are eight sites, not three, and most of them do not fail open at all.

Reading them all produced a table and three conclusions the individual comments could not
state, because each comment is correct about its own site and the problem is only visible
across them.

**Meadow does not degrade without Redis, it stops.** The single-use ws-token claim in
`realtime/wstoken.py` lets a Redis error propagate out of the handshake, so no glade
opens for anyone. `services/ratelimit.py` has no handler at all, so sign-in,
registration, sharing, a locked glade's password and ws-token minting return 500.
`services/connect.py` is the same, so no assistant can complete OAuth and in-flight
approvals are lost on a restart. Only the search nudge and the session-list notification
degrade in the way the finding assumed they all did.

**The one genuine fail-open buys availability that does not exist.**
`session_events.is_revoked` answers `False` on failure, so a session terminated from the
security screen keeps working until its access token expires. It is justified in place by
not wanting an unreachable Redis to log every user out, which is a sound argument about a
situation that cannot arise: by the time that check cannot reach Redis, the rate limiter
is refusing every sign-in and the handshake every glade, so the sessions it preserves
cannot open anything. The trade is a revoked session surviving in exchange for nothing.
Left as it stands, deliberately: changing a security default is not a documentation
change, and the refresh token that actually extends a session is checked against Postgres
regardless. It is now on the record as a decision rather than inherited from a comment,
which is the whole point of the finding.

**`/healthz` cannot observe any of it.** It answers `ok` without touching Redis or the
database, so the deploy's `--wait`, the post-deploy public curl and the container
healthcheck would all call a Redis-less stack healthy while the site is unusable.
**Fixed in 1.27.4**, which is this finding's only code change and was not in the plan:
`/readyz` reads Postgres, pings Redis and answers 503 when either is gone, and the deploy
gate and the stack check now ask for it. `/healthz` is untouched, because a liveness probe
that fails on a dependency blip would hold up a deploy that was going to recover.

One existing comment was also narrowed. `search_queue.py` says search still works without
it, a minute behind, which is true of losing the nudge because indexing also runs from a
cron. That cron runs inside arq, which is Redis-backed, so a real outage stops the
fallback too.

### Done in 1.27.2: documentation needed a currency contract (finding 18)

The review's own section 5 proposed splitting the docs into eight files. That was
declined: the drift is stale rows in a summary table, those rows go stale just as
readily in `SECURITY.md`, and splitting multiplies the places to forget while
contradicting the decision that ARCHITECTURE is the only long-lived design doc.

Section 18 is the better diagnosis of the same problem. The rule it offers is the useful
part, and needs no restructuring: where a document disagrees with the manifests or the
source, the source wins and the document is wrong.

#### How it was fixed

Done in 1.27.2, and the plan's own wording for it turned out to be wrong, which is worth
recording because it was my wording.

Item 7 said "fail a commit when ARCHITECTURE section 1 names a package absent from every
manifest". Section 1 does not survive that. Its Choice column is prose, not package
names: `PixiJS 8`, `TipTap 3 (ProseMirror)`, `pyjwt + argon2-cffi`, `PostgreSQL 16`.
Matching those to manifest keys needs an alias map, and an alias map goes stale exactly
as fast as the document it is there to check, so the rule would have become a second
thing to maintain and a source of false failures. Worse, the paragraphs around those
tables name Zustand, Tailwind, react-hook-form, Recharts and Sentry in sentences
explaining that each was dropped, so a prose scan fails on precisely the text that
records the reversal, which is the text this project most wants people to write.

What is checkable without any map is a workspace directory, because it is an exact
string. So the rule is about section 2, the repository layout, and compares the
backticked `apps/*` and `packages/*` paths there against the package manifests in the
index, in both directions, plus the count sentence that spells the number out in words.
A package on disk and absent from section 2 fails the commit. A package named in section
2 and gone from the workspace fails it too.

Scoping to section 2 is what makes it work rather than appear to, and it was not the
first attempt. The first version scanned the whole document, and the test that replays
the real 1.26.0 drift passed it: `packages/document-core` is named nine times in section
4, so a document-wide scan called the layout current while section 2 still said three
packages. Section 2 is the layout, so section 2 is what must match, and a package named
in a milestone section stays there as history rather than becoming a claim about today.

The rule runs only when a commit touches a manifest, `pnpm-workspace.yaml` or the
document itself, so an ordinary change is never failed over a package it did not look at,
and it reads the index rather than the disk for the same reason every other rule in that
file does: what is being committed is the only thing that matters.

Checked against five scenarios in a throwaway clone: a new undocumented package fails on
both the list and the count; a phantom package in section 2 fails on the list; the real
1.26.0 drift fails on both; a version bump across every manifest with the document
correct runs the rule and passes; and a commit touching neither a manifest nor the
document does not run it at all. The matching rule is stated in `.claude/CLAUDE.md`, since
the hook's own message tells a reader that is where its rules come from.

### Valid, narrowly: disaster recovery (finding 15)

Better than the review assumed. `docs/DEPLOY.md:250-300` has a verified-dump pre-deploy
procedure, a documented `pg_restore` path, 24-hour dumps pruned after seven days, and a
healthcheck that watches the newest file rather than the process, because a backup job's
failure mode is running happily and producing nothing. That last point is sharper than
anything the review says about backups.

Three gaps are real. There is no stated RPO or RTO. There is no restore rehearsal
cadence, and the review's best line applies: a backup that has never been restored is
not a verified backup strategy. Most importantly the dumps sit on the same VPS as the
database they came from, so a single-box failure takes the backups with it.

**Confirmed, not assumed.** Nothing in the repository copies a dump anywhere:
`docker/backup/`, `docs/DEPLOY.md` and the workflows contain no `rclone`, `rsync`,
`restic`, `scp` or S3 client. On the box the dumps are a plain directory,
`/srv/meadow-backups`, on the same filesystem as the database. So the only copy of the
recovery story lives on the machine it is meant to recover.

Note the floor: WAL archiving and point-in-time recovery are explicitly out of scope
(ARCHITECTURE section 13), so the achievable RPO is about 24 hours by design. Stating
that is the point, rather than leaving a reader to assume better.

**What the data is worth knowing, because it decides the remedy.** The dumps are small
and grow slowly:

| | |
|---|---|
| A dump today | about 3.8 MB, custom format, compressed |
| Growth | 3.295 MB on 26-Sep to 3.808 MB on 04-Oct, about 62 KB a day |
| Cadence | one a day, plus one before each deploy |
| Retention on the box | 7 days, by file age |

That size is the useful fact: a year of daily dumps at the current rate is on the order
of a gigabyte, so the off-host copy is not a storage problem and does not need a storage
budget. It needs a destination, a credential, and encryption, because a database dump in
somebody else's storage is the users' data.

Two smaller things the listing shows. Deploy days produce a cluster of dumps, because the
container takes one on start and every `up -d` restarts it; retention is by age rather
than by count, so this costs files and not history. And the dumps are owned by root,
which is what the compose file's `BACKUP_UID` was meant to avoid, so reading them off the
host is a `sudo` operation. Neither is urgent; both belong to whoever writes the sync.

### Done in 1.27.1: the `preview` guarantee had no test (finding 19)

No property-based testing framework is installed, confirmed against `pyproject.toml` and
`uv.lock`. Of the six properties the review lists, convergence and compaction are
already tested by example (`tests/test_concurrency.py`, including
`test_two_compaction_workers_do_not_double_fold` and
`test_an_update_committing_during_compaction_survives`, plus
`packages/document-core/src/convergence.test.ts`).

The concrete gap was that `preview: true` is a documented guarantee of every MCP write
and `packages/mcp/test/` did not test it at all. Generative testing for the rest is a
nice-to-have; this one was a promise made to callers with nothing holding it.

#### How it was fixed

Done in 1.27.1, in `packages/mcp/test/preview.test.ts`, and the shape of it came from
asking what could actually break the promise rather than from the sentence the review
wrote. Two things can, and only one of them is in the write path.

**The write path reduces to a single seam.** Every write tool that edits an existing
glade goes through one closure, `edit` in `server.ts`: it plans a batch, and on a preview
hands that batch to `previewCopy` rather than to `applyEdits`. `previewCopy` builds a
fresh `Y.Doc` from the glade's current state, applies the plan to that, and throws it
away. So the guarantee for all seven tools is one property of one function, and the test
asserts it over every shape of batch the tools can produce: `create_nodes`, `connect`,
`update_objects`, `delete_objects`, `set_text`, `apply_diagram` and `tidy_layout`, each
planned exactly as its tool plans it. The assertion is byte-identity of
`Y.encodeStateAsUpdate` on the glade's own document.

Two guards keep that from passing vacuously. Each case asserts the planned batch was not
empty, because byte-identity after doing nothing proves nothing, and asserts the copy's
bytes *did* change, so the test cannot pass by both halves being inert. One further case
previews the same plan twice and then applies it, which catches a preview that consumed
the plan it was handed.

**The second way to break it is the argument never arriving**, and no test of the write
path can see it. A write tool that simply forgets to declare `preview` in its input
schema has it stripped as an unknown key, and then applies the write: the same silent
failure by a different route. So the second half connects a real server over the SDK's
in-memory transport, reads the tool list back the way a client would, and requires every
tool taking a `glade_id` to offer `preview`.

The exemption list there names the readers rather than the writers, which is the decision
worth recording. Listing the writers would mean a new write tool is unguarded until
somebody remembers to add it, and nobody remembers. Naming the readers fails closed: a
new write tool is caught the day it lands, and a new read-only tool has to be exempted on
purpose. The test also asserts every name on that list still exists, so a renamed reader
cannot leave a stale exemption behind.

Both halves were confirmed by breaking the code they guard, which is the only way to know
a test is load-bearing rather than decorative. Pointing `previewCopy` at the live session
instead of the copy fails eight of the nine tests; dropping `preview` from `set_text`
fails the ninth, naming the tool in the message. No source file changed.

`move_lea_page` and `import_glade` are the two writes outside this. `move_lea_page` does
not go through `edit`: its preview computes the reordered page list in memory and never
calls `movePage` at all, so there is no write to suppress, and it is covered by the schema
half rather than the byte-identity half. `import_glade` and `create_glade` create the
glade they write to, so there is no existing document for a preview to protect; they are
absent from both the writer check and the reader list on purpose.

### Mostly already done: adversarial testing (finding 12)

The review lists eight adversarial scenarios to build. Most exist, across 8,241 lines of
API tests:

| Scenario | Where |
|---|---|
| Viewer sends a forged update | `test_ws_handshake.py::test_a_viewer_write_never_reaches_the_live_room` |
| Viewer write dropped, role reported | `test_ws_handshake.py::test_viewer_updates_are_dropped_and_the_role_is_reported` |
| Token expires mid-session | `test_ws_handshake.py::test_room_closes_when_the_access_token_expires_mid_session` |
| Token minted for another board | `test_ws_handshake.py::test_token_minted_for_another_board_is_forbidden` |
| Access revoked | `test_permissions.py::test_revoking_a_board_share_closes_the_door_immediately` |
| Malformed update fuzzing | `test_concurrency.py::test_garbage_on_the_wire_never_takes_the_room_down` |

The fuzzing is parametrized over seven crafted payloads, including an empty frame, a
truncated varuint, an update for a different document and an unknown message type, and
asserts the room still accepts real work afterwards, which is the half that matters.

**Corrected: the grant boundary is tested after all.** This file first recorded it as the
one real gap, on the strength of grepping `services/api/tests`. Running the suite showed
otherwise: `pnpm e2e:mcp` covers it end to end, and names the boundary in the assertion.

    PASS  deleting where only edit was granted is refused, naming the boundary
    PASS  editing where edit was granted works
    PASS  editing where only delete was granted is refused

So `GrantedChannel` has coverage, and finding 12 is answered. What remains is narrower
than a gap: the coverage lives only in an end-to-end script, and CI runs those by hand,
so nothing checks it automatically. That is the subject of finding 22 below rather than
of this one. A pytest-level case would still be cheap and would run on every commit, but
it duplicates a guarantee that is already held somewhere.

The lesson is about method, not about this test. Absence in a grep is not absence in the
suite, and three of the review's findings as well as this file's own first pass were
wrong in exactly that direction.

### Measure before changing: memory bounds, backpressure, failure injection (findings 8, 14, 20)

All three are reasonable as questions and premature as changes.

On memory (finding 8), the distinction between rendering scalability and document-state
scalability is sound, and ARCHITECTURE section 12 already lists the soak test, the
per-room memory cost and the 20k frame time as known-unmeasured. The 20,000-object OOM
is a recorded fact, not a hypothesis. The remedies suggested, document segmentation and
snapshot boundaries, are large redesigns that would collide with the locked CRDT schema.
Measuring first is not a delay here, it is the only way to know which of them is even
the right one.

On backpressure (finding 14), `PostgresYStore` does write on the realtime path, so
Postgres latency can reach realtime. But the decoupling precedent already exists:
`app/realtime/search_queue.py` pushes text indexing to Redis and fails open, and
compaction already runs on the arq worker behind a Postgres advisory lock. The reason
the update write is synchronous is durability, and buffering it trades the data-loss
guarantee for latency. That trade needs a measurement showing Postgres is actually the
constraint, which nobody has taken.

On failure injection (finding 20), `tests/test_realtime_resilience.py` already covers
departed peers, send failures, a failing room task and a mass disconnect. Missing are
database timeout, Redis timeout and a crash part-way through persistence, which overlap
finding 14 closely enough that one measurement serves both.

### Already documented: performance needs broader hardware validation (finding 7)

The review warns the project may be over-claiming its performance. It is explicitly
under-claiming, in writing, in the file a reader is pointed to. `docs/DECISIONS.md:142-143`:

> 60fps at 5,000 objects: **not verified.** Every run so far rasterised in software,
> where the render call returns before rasterisation finishes, so it measures CPU work
> only. Needs real hardware.
>
> 20,000 objects: **never measured.** The dev machine OOM-kills the run at that size.

A device matrix across low-end, mid-range and desktop hardware would be genuinely
useful, but as new measurement work rather than as a correction. It needs hardware this
project may not have, which is why the claim was marked unverified instead of being
quietly made anyway.

### Already documented and deliberate: process-local rooms (findings 3, 6, 21)

Stated three times by the review as three findings. Correct on the mechanics: rooms are
in-process, so a second API replica would hold its own `YRoom` for the same board and
the two halves would meet only through the Postgres update log.

This is known, chosen, and written down in three places. `app/realtime/rooms.py:25-29`
says it in prose, ending "single-instance for v1, and the shape that would change is
documented rather than half-built". ARCHITECTURE line 2250 says "The API runs a single
uvicorn worker, and this is a ceiling, not a default" and names the Redis-backed room
registry as v2 work. The deployment runs one worker for exactly this reason.

The review treats a documented architectural boundary as an undiscovered risk. The one
thing it asks for that genuinely does not exist is a written design for room ownership,
migration, presence propagation and fan-out. That is v2 design work, not a flaw, and
writing it before v2 starts would date badly.

### Already done, better than asked: room hotspots (finding 9)

The review asks for room-level limits and a list of metrics to measure.
`docs/DECISIONS.md:177-216` already derives the fan-out law

    frames/s = E x (E - 1) x r

validates it against measurement to within 0.05 per cent (E=400, r=1: model 158,204/s,
measured 158,187/s), derives the sustainable room size as `E ~ sqrt(F / r)`, which puts
the boundary near 124 editors at one edit per second, and confirms it empirically: 100
editors kept up with a 0.27 second drain, 200 did not at 23.9 seconds. It also shows
that because the relationship is a square root, an eight-fold faster core buys under
three times the room.

The limit is enforced as well as modelled: `max_clients_per_room` closes a joining
socket with 4429 at `app/main.py:270`. A validated model is a stronger answer than the
table of metrics the review requested.

### Wrong channel: shadow-document validation (finding 13)

The review's premise is that the server applies every incoming update to a shadow
document to work out what it does, and that this security mechanism could become the
bottleneck under load. The mechanism exists; it is not where the review puts it.

Three channels are chosen at handshake time in `app/main.py:274`:

- a full editor gets a plain `FastAPIChannel`, with no shadow apply at all;
- a viewer gets read-only filtering that reads one varuint message type
  (`app/realtime/guard.py:46`), which is close to free;
- only `GrantedChannel` replays the update on a copy of the board via `effect_of`
  (`app/realtime/guard.py:256`), and it is used solely for fine-grained API tokens
  holding edit without delete, or delete without edit.

So the expensive path is a narrow MCP-token case and is not in front of human editors at
all. Worth benchmarking if MCP traffic grows, which is item 9, but it is not the
bottleneck the review describes.

workflow. All five entry points are now in `ci.yml`, `readme:shots` among them with its
images kept as a build artifact, and `check-staged.mjs` refuses a commit that adds a

Not raised by the review, found while verifying the extraction in 1.26.0, and recorded
here because it is the most consequential thing the exercise turned up.

## Plan

Four tiers. Nothing in any of them changes the CRDT schema.

### Tier 0: the one that loses data - done in 1.27.0

1. **Copy each verified dump off the box.** Promoted to the front, ahead of everything
   else, because the open question it waited on is answered: nothing does this today, and
   the dumps live on the same filesystem as the database they recover. Every other open
   item degrades service; this one is the only one where a single event destroys data and
   no later action brings it back.

   The existing `docker/backup/backup.sh` is the right place. It already knows the moment
   a dump is verified, which is the only moment worth uploading, and it already declines
   to prune until a run succeeds. The copy goes after the rename, failures get logged and
   do not abort the loop, and the payload is encrypted before it leaves. At roughly 3.8 MB
   a day this is a small job with no storage question attached; a bucket's own lifecycle
   rule can hold the retention, rather than a second copy of the pruning logic.

2. **Write the RPO and RTO down** in `docs/DEPLOY.md`: about 24 hours and about 30
   minutes as things stand. Costs nothing, and without it a reader assumes better. If 24
   hours is too much to lose, that is the argument for revisiting the PITR decision in
   ARCHITECTURE section 13, and it should be made explicitly rather than by drift.

3. **Rehearse one restore and date it.** The dumps are verified readable, which is more
   than most projects manage, but readable is not the same as "Meadow came back up on
   it".

Items 1 and 2 shipped in 1.27.0. The upload path was exercised end to end before it was
trusted with anything: an `age` keypair, a dump sealed, pushed to a local S3 server,
fetched back and decrypted to a byte-identical file, plus the unconfigured no-op, the
refusal to upload without a recipient, and all four states of the healthcheck. What is
left is the part that cannot be done from here: the bucket, the token, the lifecycle rule
and the keypair are the operator's, and **item 3 is still outstanding** and is the one
that turns a backup into a verified one. `docs/DEPLOY.md` carries the procedure and a
line to date it.

### Tier 3: operation ids and AI mutation audit

**9. Thread an operation id and audit AI mutations. Done in 1.28.0.** One id per tool
call, minted in the MCP server's `edit` closure, tagging the Y.Doc transaction that the
write produces and filing the row that records the call. `mcp_events` holds the actor,
the glade, the token, the tool, requested against accepted, the duration and the outcome
with its reason. `McpOrigin` lives in `document-core`, which is where this item said it
belonged and was right: the id is minted on the MCP side and read on the write path, and
both sit behind one package boundary.

**One part of this item could not be built as written, and the wording was mine.** It
said the id would be "carried through the websocket". A Yjs update is a binary diff and
carries no origin: the origin is local metadata on the transaction that produced the
update and is never encoded into it. Recovering it on the server would mean inventing a
protocol message type and teaching the read-only guard in `app/realtime/guard.py` to
understand it, which is a change to the security boundary bought with information that
an explicit event carries better. The MCP server posts the event to the API instead,
which is also the only way the server learns what only the caller knows: which tool ran,
how much it asked for, and how long it took.

The counts are kept as a pair rather than a total. `requested` and `accepted` differ when
a plan names objects that are no longer on the glade, and that gap is the most useful
thing a row can say about a model working from a stale reading.

Three items in this review have now turned out to be wrong in their own wording: 5, 7 and
this one. All three were written by me, and all three were wrong in the same direction,
describing a mechanism before checking that the mechanism exists.
